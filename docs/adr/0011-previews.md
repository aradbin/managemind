# ADR 0011: Pull request previews and their databases

- Status: Accepted
- Date: 2026-10-10
- Builds on: Q1 (Oct 9: shared preview database), ADR 0009 (roles), ADR 0002 (Hyperdrive)

## Context

The Phase 0 plan asks for this on every pull request:

- a working API and storefront;
- a smoke test against them;
- the URLs posted on the PR;
- a database that is shared by default, with a PR's own Neon branch when it is labeled `db-branch`.

The plan proposed preview *versions* of two fixed Workers (`wrangler versions upload --preview-alias pr-<n>`) and a separate `db-branch.yml` workflow.

Three findings changed that design.

1. **Service bindings reach only the deployed version.** The storefront calls the API over a service binding, which always reaches the Worker's deployed version. A storefront preview alias would therefore talk to whichever API version was last deployed, not to its own PR's API.
2. **Version URLs have hard limits.** Cloudflare's preview URL documentation (checked Oct 10) says:
   - "Version URLs are not generated for Workers that implement a Durable Object." The rate limiter is a Durable Object (ADR 0006) and arrives in Phase 1.
   - "You cannot view logs for Version URLs with Workers Logs." The agent debugs through Workers Logs, because `wrangler tail` needs WebSockets.
3. **A Neon branch starts with its parent's role passwords.** A preview branch created from `production` would carry production's owner password into every preview.

## Decision

### Workers: a pair per PR, deleted when the PR closes

- **Names:** `managemind-api-pr-<n>` and `managemind-storefront-pr-<n>`, both deployed with `wrangler deploy` to `*.<account>.workers.dev`. The storefront's `API` binding points at its own PR's API.
- **Configs:** generated by `scripts/preview/workers.ts`. For the API it starts from `apps/api/wrangler.jsonc`; for the storefront it edits the Astro adapter's generated `dist/server/wrangler.json`.
- **What changes in preview:**
  - `ENVIRONMENT=preview`, which turns on the dev store selector (`?store=<slug>`);
  - `STORE_DOMAIN` set to the workers.dev domain;
  - the PR's Hyperdrive config;
  - no Cron Trigger, so previews never use one of the account's 5;
  - no queue consumer. Outbox events go to `managemind-outbox-preview`, which nothing consumes, and expire there;
  - version preview URLs off.
- **Cleanup:** closing the PR deletes both Workers. Previews add 2 scripts per open PR against the free plan's 100.

### Databases

| PR | Neon branch | Hyperdrive config | Migrations |
| --- | --- | --- | --- |
| Default | `preview`, shared, created from `production` on first use | `managemind-preview` | The PR's own, when they match master's. If the PR changes `packages/db/migrations`, the shared branch is **not** migrated and the comment says so; add `db-branch` |
| Labeled `db-branch` | `pr-<n>`, created from `production` | `managemind-pr-<n>` | The PR's own, on every push |

`scripts/preview/database.ts` runs these steps:

1. **Branch:** finds or creates the branch, with a fixed 0.25 CU compute that suspends when idle.
2. **Owner password:** resets the owner password on every branch it creates, so production's password never reaches a preview.
3. **Schema and data:** applies the migrations and the demo seed as the owner role.
4. **Hyperdrive:** when the config doesn't exist yet, it creates the `mm_app` login role in `app_rw` (with SQL, so it never joins `neon_superuser`; ADR 0009) with a generated password. It then creates the Hyperdrive config with caching off. The password exists only in the role and the config; it is masked in the job log and never stored.
5. **Concurrency:** steps 3 and 4 run under a Postgres advisory lock, so PRs that deploy at the same moment take turns on the shared branch.

Removing the label deletes `pr-<n>` and its Hyperdrive config on the next deploy, and closing the PR deletes them too. The shared branch is never deleted by a workflow.

### One workflow

`preview.yml` handles opened, synchronize, reopened, `db-branch` labeled or unlabeled, and closed. A single workflow means the database choice and the deploy can never race each other, which two workflows for the same PR could. `ci.yml` stays the fast lint, typecheck and test gate.

**Each deploy:**

1. builds;
2. sets up the database;
3. writes the configs;
4. deploys the API, then the storefront;
5. runs the Playwright smoke test (`e2e/`);
6. creates or updates the PR's single preview comment with the URLs, the database used and the smoke result.

## Consequences

- **Cost:**
  - Each open PR keeps 2 Workers.
  - A labeled PR also keeps 1 Neon branch (free plan: 10 per project) and 1 Hyperdrive config.
  - Every preview compute shares the project's 100 CU-hours a month and suspends after 5 idle minutes. Smoke tests wake it for about 5 minutes per push.
- **Stale previews:** a PR closed while Actions is down leaves its Workers behind. They are cheap and named after the PR, so they are easy to find; a scheduled sweep can be added if that ever happens.
- **The shared branch follows master's migrations, not production's.** Until `deploy.yml` (PR 18) migrates production, the shared branch can be ahead of production. That is fine for previews.
- **Unexercised in previews:** queue consumption and the daily batch. Both are covered by the integration tests and run in production.
- **Spike branch:** the `spike` branch (Phase 0, kept until Phase 1 ends) was created from `production` before this rule existed. Resetting production's `neondb_owner` password once, and updating `DATABASE_URL_MIGRATIONS` to match, closes that gap.
