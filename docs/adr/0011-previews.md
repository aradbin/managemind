# ADR 0011: Pull request previews and their databases

- Status: Accepted. Amended Oct 18: what a preview runs is budgeted. Amended Oct 23: previews connect to Neon directly, and only the CPU step uses Hyperdrive. Amended Oct 25: a full run goes through Hyperdrive again (below).
- Date: 2026-10-10
- Builds on: Q1 (Oct 9: shared preview database), ADR 0009 (roles), ADR 0002 (Hyperdrive)

## Context

The Phase 0 plan asks for this on every pull request:

- a working API and storefront;
- a smoke test against them;
- the URLs posted on the PR;
- a database that is shared by default, with a PR's own Neon branch when it is labeled `db-branch`.

The plan proposed preview *versions* of two fixed Workers (`wrangler versions upload --preview-alias pr-<n>`) and a separate `db-branch.yml` workflow.

Three findings changed that design.

1. **Service bindings reach only the deployed version.** The storefront calls the API over a service binding, which always reaches the Worker's deployed version. A storefront preview alias would therefore talk to whichever API version was last deployed, not to its own PR's API.
2. **Version URLs have hard limits.** Cloudflare's preview URL documentation (checked Oct 10) says:
   - "Version URLs are not generated for Workers that implement a Durable Object." The rate limiter is a Durable Object (ADR 0006) and arrives in Phase 1.
   - "You cannot view logs for Version URLs with Workers Logs." The agent debugs through Workers Logs, because `wrangler tail` needs WebSockets.
3. **A Neon branch starts with its parent's role passwords.** A preview branch created from `production` would carry production's owner password into every preview.

## Decision

### Workers: a pair per PR, deleted when the PR closes

- **Names:** `managemind-api-pr-<n>` and `managemind-storefront-pr-<n>`, both deployed with `wrangler deploy` to `*.<account>.workers.dev`. The storefront's `API` binding points at its own PR's API.
- **Configs:** generated by `scripts/preview/workers.ts`. For the API it starts from `apps/api/wrangler.jsonc`; for the storefront it edits the Astro adapter's generated `dist/server/wrangler.json`.
- **What changes in preview:**
  - `ENVIRONMENT=preview`, which turns on the dev store selector (`?store=<slug>`);
  - `STORE_DOMAIN` set to the workers.dev domain;
  - the PR's Hyperdrive config;
  - no Cron Trigger, so previews never use one of the account's 5;
  - its own outbox queue, `managemind-outbox-pr-<n>`, which it consumes (amended Oct 19, Phase 5A). The events send the preview's notifications to the dev mailbox. A preview binds no `EDGE` store and no Turnstile token, so nothing else happens. Closing the PR deletes the queue;
  - version preview URLs off.
- **Cleanup:** closing the PR deletes both Workers. Previews add 2 scripts per open PR against the free plan's 100.

### Databases

| PR | Neon branch | Hyperdrive config | Migrations |
| --- | --- | --- | --- |
| Default | `preview`, shared, created from `production` on first use | `managemind-preview` | The PR's own, when they match master's. If the PR changes `packages/db/migrations`, the shared branch is **not** migrated and the comment says so; add `db-branch` |
| Labeled `db-branch` | `pr-<n>`, created from `production` | `managemind-pr-<n>` | The PR's own, on every push |

`scripts/preview/database.ts` runs these steps:

1. **Branch:** finds or creates the branch, with a fixed 0.25 CU compute that suspends when idle.
2. **Owner password:** resets the owner password on every branch it creates, so production's password never reaches a preview.
3. **Schema and data:** applies the migrations and the demo seed as the owner role.
4. **Hyperdrive:** when the config doesn't exist yet, it creates the `mm_app` login role in `app_rw` (with SQL, so it never joins `neon_superuser`; ADR 0009) with a generated password. It then creates the Hyperdrive config with caching off. The password exists only in the role and the config; it is masked in the job log and never stored.
5. **Concurrency:** steps 3 and 4 run under a Postgres advisory lock, so PRs that deploy at the same moment take turns on the shared branch.

Removing the label deletes `pr-<n>` and its Hyperdrive config on the next deploy, and closing the PR deletes them too. The shared branch is never deleted by a workflow.

### One workflow

`preview.yml` handles opened, synchronize, reopened, `db-branch` labeled or unlabeled, and closed. A single workflow means the database choice and the deploy can never race each other, which two workflows for the same PR could. `ci.yml` stays the fast lint, typecheck and test gate.

**Each deploy:**

1. builds;
2. sets up the database;
3. writes the configs;
4. deploys the API, then the storefront;
5. runs the Playwright smoke test (`e2e/`);
6. creates or updates the PR's single preview comment with the URLs, the database used and the smoke result.

## Consequences

- **Cost:**
  - Each open PR keeps 2 Workers.
  - A labeled PR also keeps 1 Neon branch (free plan: 10 per project) and 1 Hyperdrive config.
  - Every preview compute shares the project's 100 CU-hours a month and suspends after 5 idle minutes. Smoke tests wake it for about 5 minutes per push.
- **Stale previews:** a PR closed while Actions is down leaves its Workers behind. They are cheap and named after the PR, so they are easy to find; a scheduled sweep can be added if that ever happens.
- **The shared branch follows master's migrations, not production's.** Until `deploy.yml` (PR 18) migrates production, the shared branch can be ahead of production. That is fine for previews.
- **Unexercised in previews:** queue consumption and the daily batch. Both are covered by the integration tests and run in production.
- **Spike branch:** the `spike` branch (Phase 0, kept until Phase 1 ends) was created from `production` before this rule existed. Resetting production's `neondb_owner` password once, and updating `DATABASE_URL_MIGRATIONS` to match, closes that gap.

## Amendment (Oct 18): what a preview runs

Every environment shares the account's 100,000 Hyperdrive queries a day. On Oct 18, preview runs used 97% of 125,140 queries, and Hyperdrive refused production's connections until the 00:00 UTC reset (phase-4 report §4). A full run (E2E flows, CPU step, Lighthouse) costs about 25,000 queries. A smoke run costs a few hundred.

1. **A PR that changes only docs** (`docs/` and `*.md`) gets no preview. Its comment says so.
2. **By default**, a preview deploys and runs only the smoke project.
3. **The `full-preview` label** adds the E2E flows, the CPU step and Lighthouse, while the UTC day's Hyperdrive count is at most 50,000. Past that, or if the count can't be read, the run is smoke only, and the comment says why. Adding the label starts a run; removing it doesn't.
4. **Before merging a PR that changes code, it gets one full run.** The label stays on for later pushes, but those check the budget again.

`scripts/preview/scope.ts` decides, and `preview/choose.ts` reads the count from GraphQL Analytics. On Workers Paid, Hyperdrive has no daily limit, and the ceiling can go.

## Amendment (Oct 23): previews without Hyperdrive

The Oct 18 budget didn't stop it happening again: preview runs used up the day's Hyperdrive queries once more, and production's database answered again only after the reset (phase-5a-report §5). The owner chose (phase-5b-plan Q3) to take previews off Hyperdrive, except for the one step that needs it.

**Nothing on a preview needs Hyperdrive to work.** The API's `pg` client takes any connection string. **The CPU step depends on it:** its numbers check ADR 0003's budgets and ADR 0013's trigger for Workers Paid. Without Hyperdrive, each request sets up its own TLS connection and authenticates, CPU that production never spends, so the numbers would come out worse than production's.

1. **The PR's own login role.** `preview/database.ts` gives `mm_app_pr_<n>`, a member of `app_rw` like `mm_app`, a new password on every deploy. It writes the role's URL, through the branch's pooler (`-pooler`, PgBouncer in transaction mode), to a file only the deploy step reads into the API's `DATABASE_URL` secret. Each PR has its own role on the shared branch, so one PR's new password never signs another's preview out. Tenant context is set per transaction (`set_config(…, true)`), which the transaction pooler keeps correct. Closing the PR drops the role.
2. **The API prefers Hyperdrive when it's bound** (`apps/api/src/db.ts`), and its preview config has no binding. Production always has it, and `production/workers.ts` still requires it.
3. **The smoke tests, the E2E flows and Lighthouse** run on that direct connection, and use no Hyperdrive queries. Lighthouse's budgets stay the same. If slower queries make them fail on previews, that is reported and not loosened.
4. **The CPU step** (full runs only) deploys the same API again with `wrangler.preview-hyperdrive.json`, bound to the PR's Hyperdrive config, and measures only its own requests after that deploy. Then the API is deployed again on the direct connection. The E2E's import chunks are no longer in its table.
5. **The ceiling now gates only the CPU step.** A labelled run always runs the E2E flows and Lighthouse. Past 50,000 queries, or when the count can't be read, it skips the CPU step and says so. On Workers Paid (from the first pilot client, phase-5b-plan Q2), the ceiling can go.

**Cost:** previews' queries are a little slower, with no pooling at the edge. Neon's compute use is unchanged, since Hyperdrive's caching was already off on previews.

## Amendment (Oct 25): full runs through Hyperdrive again

On the direct connection, the Free plan's 10 ms CPU limit stopped too many of a full run's requests. #75's preview failed twice in the older flows, with no bug in them. Workers Observability records those empty 503s as `outcome: exceededCpu`, not as connection failures. The same requests, sent to a master preview at the same time, used about as much CPU and weren't stopped. So Cloudflare's enforcement varies, and a full run can't depend on it. The "empty 503s" of phase-5b-report §3 were most likely the same thing. The owner chose to put full runs back on Hyperdrive.

1. **A full run deploys the API bound to Hyperdrive before the tests.** The E2E flows, Lighthouse and the CPU step all run on it. The CPU step still measures only its own requests, from its start.
2. **Afterwards the API is deployed on the direct connection again**, even after a failure or a cancel. Trying a preview by hand still uses no Hyperdrive queries.
3. **A smoke-only run stays on the direct connection.** It is a few requests.
4. **The E2E runs one flow at a time** (`workers: 1` in CI). Through Hyperdrive, two runs still had 8 requests stopped, in bursts while two heavy flows overlapped. One worker spreads the same CPU over about twice the time, roughly 17 minutes of E2E instead of 9.
5. **A PR may narrow its full run** with the `narrow-preview` label, on top of `full-preview`. The E2E is then the smoke tests and the spec files the PR adds, run with `--no-deps`: each flow runs on the run's freshly seeded store without the flows it normally follows. One worker didn't get #75's whole suite through. The first stopped request came about 12½ minutes into the E2E, later than with two workers (about 8). That fits a CPU allowance per Worker over a window of time, which a full suite uses up, rather than a rate. Lighthouse and the CPU step still run. The flows a narrowed run skips last passed on the PR that added them; a change to them needs a whole run.
6. **The ceiling gates the run on Hyperdrive.** Past 50,000 queries today, or when the count can't be read, the E2E flows and Lighthouse run on the direct connection without the CPU step, and the comment says so. Such a run may fail as #75's did.

**Cost:** a full run uses about 25,000 of the day's 100,000 queries again (the Oct 18 measure). That is the risk the Oct 23 amendment removed. The ceiling is checked once, at the start of each run, so two full runs on one busy day can still take production close to the limit. Moving to Workers Paid removes both the CPU limit and the daily query limit.
