# ADR 0024: Stores' credentials, sealed with one platform key

- Status: Accepted. Production needs the owner's `CREDENTIALS_KEY` (phase-5a-plan §1, Q15); until then no store can save any credentials.
- Date: 2026-10-18
- Plan: phase-5a-plan §3.1, Q15. Code: `packages/core/src/credentials/`, `packages/shared/src/credentials.ts`, `apps/api/src/admin/credentials.ts`, `apps/api/src/credential-checks.ts`

## Context

Each store brings its own SSLCommerz merchant account, its own SMS gateway, and optionally its own email service. The platform must keep those secrets so that background jobs can charge, refund and send. It must also keep them away from anyone who can read the database, logs or backups, and away from other stores.

## Decision

1. **One table**, `store.provider_credentials`, holds one row per store and kind (`sslcommerz`, `sms`, `email`). It sits under RLS like every tenant table.
2. **The secret fields are one encrypted blob.** It uses AES-256-GCM through Web Crypto, with a fresh 12-byte IV per write. The key is the Worker secret `CREDENTIALS_KEY` (32 random bytes, `openssl rand -base64 32`).
   - The additional data is `tenant_id:kind:key_version`. A blob copied to another store or kind fails to decrypt, even for someone who can write rows.
   - Non-secret settings (the From address, the sender ID, the generic SMS adapter's URL) are plain JSON next to the blob.
3. **The provider is checked before saving.** A key the provider refuses, or an email domain it hasn't verified, is never stored.
4. **Secrets never come back.**
   - Lists show the provider, the mode, the last 4 characters of the store ID or key, the plain settings, and the last check.
   - Only the code that calls the provider decrypts.
   - The audit log records who changed which provider, never the secrets.
5. **Owners and managers only**, through the new `settings.credentials` permission.
6. **The key is never generated by the deploy.** A changed key makes every stored credential unreadable. The owner keeps a copy offline (PLAN.md Phase 5B), and a deploy without the key leaves online payment and SMS off and warns.
7. **Previews** use `CREDENTIALS_KEY_PREVIEW` when it exists. Otherwise each deploy makes a new key, and credentials saved on a preview last until its next push.

## Consequences

- **Rotation** is a new key version: new writes use the newest key, and a job re-encrypts old rows. The column exists; the job is written when a rotation is needed.
- **Unreadable rows don't break anything.** A blob that fails to open (a wrong key) leaves that store on the platform's own sender, and the error is logged.
- Holding the platform key is the trust boundary. Anyone with the Worker's secrets can read every store's credentials, as with any single-key vault. A per-store key buys nothing while the same Worker holds both.
