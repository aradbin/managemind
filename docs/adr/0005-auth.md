# ADR 0005: Staff and shopper authentication with Better Auth on Workers

- Status: Accepted. Decision 4 (instance caching) is superseded by ADR 0013. Decision 5's rate limits use a Durable Object, not the rate-limiting binding (ADR 0006). Decision 1 and the staff instance are amended for Phase 1 (see the amendment at the end).
- Date: 2026-10-09
- Spike code: `spikes/auth/` (deleted after Phase 1)

## Context

The plan uses Better Auth as two separate instances with the Drizzle adapter:

- **staff** in the `platform` schema, with the organization plugin for store membership;
- **shoppers** in the `store` schema, where each account belongs to one store: the email is unique per store, and RLS shows the instance only the current store.

The spike had to prove three things on Workers:

1. the two instances work with this schema;
2. two shoppers with the same email in two stores stay fully separate;
3. password hashing fits the free plan's 10 ms CPU, or we need the fallback (email codes and passkeys).

## Method

- **Database:** the throwaway Neon branch `spike`.
- **Staff tables:** `platform.users`, `sessions`, `accounts`, `verifications`, `organizations`, `members`, `invitations`.
- **Shopper tables:** `store.shopper_users`, `shopper_sessions`, `shopper_accounts`, `shopper_verifications`. Each has `tenant_id default app.current_tenant_id_guarded()`, FORCE RLS (ADR 0002's guarded policy) and, for users, `unique (tenant_id, email)`.
- **Schema mapping:** Drizzle property keys are Better Auth's field names, and the columns are snake_case. IDs are `uuidv7()` defaults (`generateId: false`).
- **Shopper requests:** every request runs inside one tenant transaction (`withTenant` from ADR 0002). The store comes from the path (`/store/A/...`, `/store/B/...`), standing in for the store host.
- **Worker:** `managemind-spike-auth` on the free plan, placed in `aws:ap-southeast-1`, with Better Auth 1.7.7 and its email-code plugin for shoppers.
- **CPU:** from Workers Logs (`$workers.cpuTimeMs`).

## Results

### Correctness (19 checks, 7 rounds, with and without instance caching, all passed)

- The same email signing in by email code in store A and store B creates **two shopper users**, one per store, with different IDs.
- Store A's session cookie on store A returns A's shopper. On store B it returns **no session**; store B's cookie returns B's shopper.
- A sign-in code issued by store A is **rejected on store B** (400).
- Staff sign-up, sign-in and wrong-password rejection work with both hash variants. Creating an organization sets it as the session's active store.
- The Drizzle adapter for Postgres never opens its own transactions. Its `transaction` option defaults to `false`, and its `db.transaction()` paths are MySQL-only. Better Auth therefore runs entirely inside our tenant transaction, and each auth request commits or rolls back as one unit.
- Cookies are named `__Secure-mm_staff.session_token` and `__Secure-mm_shop.session_token`. They are host-only, so each store's cookie stays on its own domain.

### Cookie cache allows cross-store replay

With Better Auth's optional `session.cookieCache` turned on, store B **accepted store A's session cookie**, because the session is validated from the signed cookie without a database lookup and both stores share one signing secret. With the cache off, which is the default, B rejects it, because the lookup runs under B's RLS.

### CPU per request (p50 / p90 / max, ms)

| Request | Measured |
| --- | --- |
| Hash one password, Better Auth default (native `node:crypto` scrypt, N=16384, r=16, p=1, 32 MiB) | 82 / 116 / 132 |
| Hash one password, Web Crypto PBKDF2-SHA-256, 100,000 iterations | 24 / 39 / 49 |
| Staff sign-in, scrypt | **89** / 156 / 212 |
| Staff sign-in, PBKDF2 100k | **36.5** / 61 / 73 |
| Staff get-session, instance built per request | 10.5 / 20 / 21 |
| Staff get-session, instance cached per isolate | **7** / 14 / 24 |
| Shopper get-session, inside the tenant transaction | 10–11 / 17–19 / 33 |
| Shopper send sign-in code | 11–15 / 16–20 / 29 |
| Shopper sign in with code | 17–19.5 / 20–28 / 58 |
| Build both instances with no database | 19 / 37 / 65 |

- Workers refuse PBKDF2 above **100,000 iterations** ("iteration counts above 100000 are not supported"), which is below OWASP's current recommendation of 600,000 for PBKDF2-SHA-256.
- No request was terminated. Cloudflare documents "some built-in flexibility" for Workers that *infrequently* run over the limit, but a Worker that exceeds it consistently gets error 1102.
- The bundle is 538 KiB gzipped (3.2 MiB raw) with Better Auth, the organization and email-code plugins, Drizzle and pg, which fits within the 3 MiB compressed limit.

## Options for staff sign-in on the free plan

1. **Email and password with scrypt:** about 90 ms per sign-in, 9 times the limit. Not viable on the free plan.
2. **Email and password with PBKDF2 at 100k:** about 37 ms, still 3–4 times the limit, and weaker than OWASP's recommendation, with no way to raise it on Workers.
3. **Email codes now, passkeys later:** a code sign-in is 17–20 ms, rare (a few per staff member per day), and does no password hashing. Passkey verification is a single native ECDSA check.

## Decision

1. **Two Better Auth instances, as planned:**
   - **staff** in `platform`: organization plugin, one organization per store, linked 1:1 to `platform.tenants` in Phase 1;
   - **shoppers** in `store`: `tenant_id` filled by the guarded database default, `unique (tenant_id, email)`, FORCE RLS, every request inside `withTenant`.
2. **No passwords on the free plan.**
   - Staff sign in with **email codes** (optional TOTP two-factor in Phase 1), and passkeys are added when available. This is the plan's stated fallback.
   - When the platform moves to Workers Paid, email and password can be switched on with Better Auth's default scrypt without schema changes, because `accounts.password` already exists.
3. **Cookie cache off for both instances.** A config test fails CI if `session.cookieCache.enabled` is ever true. The shopper instance will also sign with a per-store secret, derived from the auth secret and the tenant ID, as defense in depth (Phase 4).
4. **Instances are cached per isolate.** Each instance is built once, and its database handle is a proxy that resolves to the current request's transaction through `AsyncLocalStorage`. This saves about 3.5 ms on every session check, the most frequent auth request.
5. **Better Auth's built-in rate limiter is off.** Rate limits use the Workers rate-limiting binding (ADR 0006).

## Consequences

- Tenant separation for shopper accounts rests on the same RLS and transaction rules as everything else. No Better Auth feature needs to understand tenants.
- **A session check costs about 7 ms of CPU on its own, and shopper requests are heavier, about 10–11 ms.** That leaves very little of the 10 ms budget for the request's actual work. ADR 0003 (CPU budget) has to decide whether to avoid a session lookup on most requests, for example by keeping catalog requests anonymous and cached, or whether this is the first trigger for Workers Paid.
- **Sign-in flows (17–20 ms) rely on the documented tolerance for infrequent overruns.** That is acceptable because they are rare, but the rate limits must keep them rare.
- **Phase 1 needs the transactional email provider** before any staff can sign in, which is already a Phase 1 prerequisite.
- **One cached shopper instance serving many store hosts needs `baseURL` and `trustedOrigins` resolved per request.** The spike used one instance per store path; Phase 4 designs the multi-host version.
- **Workers Logs records every request URL, including the query string.** Secrets must never travel in URLs: the spike's own token appears in its logs. Sign-in codes travel in POST bodies, and any future magic-link or verification token must be exchanged through a POST, or its URL must be kept out of the logs.

## Amendment: the staff instance in Phase 1 (2026-10-13)

Plan: phase-1-plan §3.3, §3.4 and §5.5. Code: `apps/api/src/auth/`.

1. **No organization plugin.** The staff instance uses Better Auth's core with the `emailOTP` and `twoFactor` plugins only. Memberships, invitations and roles live in our own tables (`packages/core/identity`), so every write goes through our permission checks and audit log, and support access can reach a store without a membership (§3.3; the owner agreed on Oct 11).
2. **Sign-in codes, no sign-up.** `disableSignUp` is on, so a code is only ever sent to an existing user, and "send code" answers the same for unknown emails. Codes are 6 digits, valid for 10 minutes, 3 tries each, and stored as a hash.
3. **Two-factor login on email codes works through the plugin's own challenge (Plan A).** The `twoFactor` plugin challenges only password sign-ins. Its single after-hook is reused with a wider matcher that also covers `/sign-in/email-otp`: a user with 2FA gets no session, only the plugin's two-factor cookie, and `verify-totp` or `verify-backup-code` then creates the session. Trusted devices and backup codes work exactly as the plugin implements them, and nothing internal is copied. Plan B (a pending flag on the session) wasn't needed. If an upgrade changes the plugin's hooks, building the instance throws, and the tests cover both directions: no session without the code, and no second challenge on a trusted device.
4. **Only the endpoints the admin uses are reachable** under `/api/auth/*`: send code, sign in, verify email, get and list sessions, sign out, revoke sessions, and enable, verify, disable and backup codes for 2FA. Everything else answers 404, including `update-user` and `delete-user`.
5. **Sessions:** 7 days, extended when used after a day. Platform users get at most 12 hours from sign-in: a database hook caps `expiresAt` both when the session is created and when it is refreshed. Turning 2FA on or off deletes the user's other sessions.
6. **CSRF:** Better Auth checks `Origin` against the admin's origin only when a cookie is sent, so the API checks every write to `/api/auth/*`, `/v1/admin/*` and `/v1/platform/*` itself: the `Origin` must be the admin's, and a body must be JSON.
7. **Rate limits** (ADR 0006) run before Better Auth: sends per IP and per email, code checks per email with the lockout, and authenticator checks per user (the challenge cookie is resolved to its user, so a new challenge doesn't reset the count).
8. **`platform.verifications.id` is text** (migration 0006). Better Auth writes its own non-UUID id there for the lock it takes when an unverified user first signs in with a code, and every invited user and new store owner starts unverified. The default stays `uuidv7()`.
